3. MODEL COMPARISON: two one-parameter models, fitted and scored separately
------------------------------------------------------------------------------------------------
H2' says the excess is proportional to drafted tokens; H2 says rejected tokens. Each is a
single free parameter, so each is identified whatever the two regressors' correlation is.

Fitted on the extensive form: excess_ms = coefficient * count, where excess_ms is
total decode time minus what the same number of plain forwards cost on that prompt.
model                         ms per token           RSS   R2 (origin)
H2'  cost per drafted               7.2083  146740745.43        0.9781
H2   cost per rejected             10.1835 1176732389.79        0.8242

  RSS(rejected model) - RSS(drafted model) = +1029991644.36 [+976369690.50, +1081965484.35]   clears zero by 18.49 half-widths
  Positive means the drafted-token model fits better.

  per-arm mean residual, so a reader can see WHERE each model fails:
    arm                        obs ms    H2 pred  H2-prime pred
    mtp-n3-p.00                2818.2     2243.6         3344.1
    mtp-n3-p.50                2606.8     1084.3         2414.5
    mtp-n3-p.75                2311.4      347.1         1701.1
    mtp-n7-p.00                6544.4     6989.5         6836.9
    mtp-n7-p.50                3801.3     2268.1         3395.1
    mtp-n7-p.75                2727.8      657.0         2022.3

  A one-token model cannot be the whole story: the drafter runs its own forward pass every
  step whether or not the gate lets it extend, so part of the excess is per STEP, not per
  token. Both models above under-predict the heavily gated arms, which is what that looks
  like. Adding the step term to each:

    model                                ms/step   ms/token             RSS       R2
    step + drafted   (H2-prime)            4.229      6.112     58599877.53   0.9912
    step + rejected  (H2)                 10.740      6.889    209452431.54   0.9687

    RSS(step+rejected) - RSS(step+drafted) = +150852554.01 [+117785290.18, +183815059.03]   clears zero by 3.57 half-widths

  WHY THIS SURVIVES A FORWARD-PASS COUNT THAT cost_model.py REFUSES TO USE.
  F comes from the same derivation whose integrity check fails on this phase, and
  cost_model.py now refuses to print k, c or k0 when it does. It does not follow that
  this comparison fails with it, and the difference is worth stating rather than
  asserting: `drafted` and `rejected` are exact counters, and F enters only through
  the offset F*tau0, so a systematic error in F moves the offset and not the
  regressors. Refitting with F shifted, which is the direction and size the
  derivation is known to be wrong by:
     F shift   one-parameter winner   ms/step  ms/token
          -2                drafted     4.481     6.140
          -1                drafted     4.355     6.126
          +0                drafted     4.229     6.112
          +1                drafted     4.105     6.098
  The winner does not change and the coefficients move by about a percent, so the
  comparison does not rest on F being exact. What it would still take from an exact
  count is the ABSOLUTE ms/step and ms/token, which are offsets away from it.

------------------------------------------------------------------------------------------------
4. JOINT FIT, reported last because it is the part that is NOT identified
------------------------------------------------------------------------------------------------
  beta_drafted : +7.57 [+7.42, +7.74]  ms per token per forward
  beta_rejected: -0.87 [-1.12, -0.68]  ms per token per forward

  One coefficient is NEGATIVE. Rejecting a draft cannot save time and neither can drafting
  one, so this is not a measurement: it is what least squares does when two regressors point
  in nearly the same direction and it splits one effect into a large positive and a small
  negative. The split is an artefact. The SUM is what the data constrains, and section 3
  is where the answer is.
