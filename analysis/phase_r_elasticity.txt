--- correction: the bandwidth lever is not clean ---
  At a fixed power cap, raising the memory clock takes power from the core, so core
  clock falls across the bandwidth sweep. A compute-elastic arm is penalised by that,
  which makes its measured bandwidth elasticity an under-estimate. Below, the core-
  clock contribution is estimated using each method's OWN compute elasticity (from the
  pw-lo -> stock interval) and removed.

  over bw-lo -> bw-hi:
    method             core MHz  measured  core term  corrected
    baseline      1799 ->  1759     0.751      0.130      0.881
    mtp-n3        1721 ->  1708     0.135      0.078      0.213
    mtp-n7        1740 ->  1728     0.115      0.066      0.182

  The correction raises every arm's bandwidth elasticity, baseline included, so
  the RATIO between them moves less than either figure does.

--- are the compute intervals matched across methods? 0 of 3 conditions ---
    condition       spread   drift   per-method core clock
    pw-vlo         35.80% 118.90%   baseline=387  mtp-n3=478  mtp-n7=525  <-- not matched
    pw-lo          30.00% 71.59%   baseline=906  mtp-n3=1081  mtp-n7=1178  <-- not matched
    stock           4.01%  6.92%   baseline=1785  mtp-n3=1716  mtp-n7=1732  <-- not matched
  spread is between methods at the same condition; drift is within an arm,
  measured as mean minus min, so 0.00 % means every sample sat on the pin.
  Where a condition is not matched the pin did not bind, because the power
  limit did first. Check the power column in the operating points above: an
  arm whose peak draw reaches the cap cannot hold its requested clock, and a
  speculative arm reaches it sooner because it draws more at the same clock.
  Elasticities crossing such a condition carry that mismatch; ones that do
  not, do not. Phase R, for contrast, was 30.0 % and 35.8 % mismatched.
