Why two result files were replaced, and what the replacements agree with.

Both originals carried host_contended incidents caused by work run on this host DURING
the measurement, but not by the same party, and the distinction is worth keeping:
Phase A's cap-1600 run took two from another session's data-perturbation suite (python3
at 100 % and 97 %); Phase B's took one from a repo-side nvidia-smi and one from a
repo-side git, and both of those were this session's own doing. Under this repository's
own audit rule an incident makes the file FAIL, and a FAIL means the result may not be
used as it stands.
Re-running is the only way to clear that; deleting the flag would not be.

Neither original is retired on the strength of the re-run alone. What follows is the
arm-by-arm comparison between each original and its replacement. Had the contention
moved the measurement, it would show as arms whose intervals do not overlap.

NOTE on the phase_b row 'matrix sha256 -- NOT RECORDED in reference'

results/phase_b.json was written on 2026-08-27, before the result schema carried
`matrix.file_sha256`, so the tool has nothing to compare and correctly declines to
call it verified. The matrix was instead checked by content, on 2026-08-28, against
what the reference file itself records about the design:

  arms and their extra_args   7 vs 7   identical: True
  COMMON_ARGS                 identical: True

That covers every input the matrix module supplies to a run. It is a weaker check
than a hash -- it compares what the old file chose to record, not the file that
produced it -- and it is stated here rather than folded into the tool's verdict so
that the distinction survives.
