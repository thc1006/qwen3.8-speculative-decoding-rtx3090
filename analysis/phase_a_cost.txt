--- TEST 1: is the overhead charged to REJECTION? ---
    Model a rejection-proportional cost r (decode-steps per rejected draft token):
        k = k_verify + r * n_max * (1 - acceptance)
        => dk/d(acceptance) = -r * n_max,   so  r = -slope / n_max
    A state-rollback account of the overhead predicts r > 0, i.e. slope < 0.

arm               n    accept range     slope     r2  r estimate  reading

mtp-n3            3  0.325-0.857    0.0070  0.028    -0.00234  r <= 0 - no rejection cost detected (k spread 1.79%)

dflash2-n7        7  0.096-0.695    0.0346  0.191    -0.00494  r <= 0 - no rejection cost detected (k spread 3.15%)

  Largest r across arms: -0.00214 decode-steps per rejected draft token.
  Acceptance spans roughly 0.096-0.918 in this data - nearly a ten-fold range -
  so a rejection-driven overhead of any consequence would have shown up here.
  Reading: the verification overhead is paid per position VERIFIED, not per
  draft REJECTED. This does not say rollback is free; it bounds how much of
  the observed cost rollback can account for.

--- implied optimum ---
    mean_len saturates with depth while k grows linearly, so speedup = mean_len/k
    has an interior maximum in principle. Over the widths measured here it falls
    monotonically, so what follows is the best TESTED point, not a fitted optimum:
  draft-dflash   n4=1.519x  n7=1.226x   -> best n-max = 4
  draft-mtp      n2=1.598x  n3=1.523x  n5=1.321x   -> best n-max = 2
